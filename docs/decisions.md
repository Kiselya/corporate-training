## DR-001: Next.js vs Django -- выбор фреймворка

**Дата:** День 1, начало хакатона

**Контекст:** Нужно выбрать основной фреймворк для fullstack-приложения. ТЗ требует: веб-интерфейс, REST API, диаграмму Ганта (35 баллов из 100), XML-интеграцию. Срок -- 48 часов.

**Рассмотренные варианты:**
1. **Django + DRF + React (отдельно)** -- зрелый бэкенд, но два проекта, два деплоя, CORS
2. **Express + React (монорепо)** -- гибко, но много boilerplate (роутинг, middleware, структура)
3. **Next.js 16 (App Router)** -- fullstack в одном проекте, файловая маршрутизация, React из коробки

**Выбор:** Next.js 16 (App Router)

**Обоснование:**
- Диаграмма Ганта -- ключевой компонент (35 баллов). Это интерактивный SVG: масштабирование, тултипы, прогресс-бары, клики. Django отдавал бы статичный HTML, для интерактивности все равно нужен JS-фреймворк -- то есть мы бы строили два приложения вместо одного.
- App Router: `src/app/api/groups/route.ts` -> `GET /api/groups`. Нет ручной настройки роутинга.
- Server Components + Client Components: серверный рендеринг для SEO/первой загрузки, клиентская интерактивность для Ганта.
- Один Docker-контейнер вместо двух (Django + React SPA).

**Компромиссы:**
- Django Admin Panel -- мы потеряли готовый интерфейс администрирования. Компенсировано кастомной страницей `/admin` с управлением пользователями.
- Python-экосистема (pandas, numpy) -- не доступна. Для наших расчетов (суммы, проценты) JavaScript достаточен.
- Next.js 16 -- свежая версия, возможны breaking changes. Митигация: читаем документацию из `node_modules/next/dist/docs/`.

## DR-002: PostgreSQL vs Supabase -- выбор базы данных

**Дата:** День 1

**Контекст:** Нужна реляционная СУБД для 13 моделей данных. Вариант SaaS (Supabase) позволяет сэкономить время на настройку.

**Рассмотренные варианты:**
1. **Supabase (hosted PostgreSQL)** -- мгновенный старт, встроенная аутентификация, real-time
2. **PostgreSQL (self-hosted через Docker)** -- стандартный подход, `docker-compose.yml`
3. **SQLite** -- ноль конфигурации, файл рядом с проектом
4. **MongoDB Atlas** -- NoSQL, гибкая схема

**Выбор:** PostgreSQL (self-hosted)

**Обоснование:**
- Vendor lock-in: Supabase привязывает к их платформе. Заказчик хакатона должен иметь возможность развернуть систему на своем сервере -- `docker-compose up` и готово.
- Реляционная модель: FK-связи (Company -> Employee -> GroupMember -> TrainingGroup -> Course) критичны для целостности данных. MongoDB потребовала бы денормализацию и ручной контроль целостности.
- JSON-поля: PostgreSQL нативно поддерживает `jsonb` -- используется для `customFields` компании и `details` в IntegrationLog.
- SQLite: ограничения конкурентности (один writer), нет полноценных FK. Не подходит для корпоративной системы.

**Компромиссы:**
- Supabase дает real-time подписки и встроенную аутентификацию -- мы реализовали эти функции самостоятельно (JWT + polling).
- Нужен Docker для локальной разработки (vs SQLite -- нулевая конфигурация).

## DR-003: Кастомная диаграмма Ганта vs готовая библиотека

**Дата:** День 1

**Контекст:** Диаграмма Ганта -- 35 баллов из 100. Требования: шкала времени, полоса группы обучения, прогресс, тултипы с бизнес-данными, масштабирование.

**Рассмотренные варианты:**
1. **dhtmlx-gantt** -- зрелая библиотека, but GPL/коммерческая лицензия, тяжелый бандл (~300 KB), сложная кастомизация прогресса внутри полос
2. **frappe-gantt** -- легкая (MIT), но ограниченный API: нет тултипов с кастомным содержимым, нет масштабирования квартал
3. **Кастомный React/SVG** -- полный контроль, но нужно писать с нуля

**Выбор:** Кастомная реализация на React/SVG

**Обоснование:**
- Прогресс внутри полосы: ни одна из библиотек не позволяет нативно рисовать заполнение внутри временной полосы. В кастомном SVG -- это два `<rect>`: фон и прогресс с `opacity: 0.7`.
- Тултипы с бизнес-данными: курс, количество участников, прогресс-бар CSS -- HTML-оверлей поверх SVG. Библиотеки дают только текстовые тултипы.
- Масштабирование: неделя (дни), месяц (номера недель), квартал (только месяцы) -- кастомная логика шкалы, подстройка `dayWidth` под каждый режим.
- Лицензия: dhtmlx-gantt требует GPL или покупку коммерческой лицензии. Для передачи заказчику неприемлемо.

**Компромиссы:**
- Время разработки: ~6 часов на Ганта (vs ~1 час на подключение библиотеки).
- Нет drag & drop для перемещения полос (не требовалось по ТЗ).
- Нет dependency arrows между задачами (не требовалось).
- Результат: 483 строки TypeScript -- полностью контролируемый компонент.

## DR-004: JWT (jsonwebtoken + jose) vs NextAuth sessions

**Дата:** День 1

**Контекст:** Нужна аутентификация с ролями (SUPER_ADMIN, ADMIN, USER). Next.js middleware работает в Edge Runtime.

**Рассмотренные варианты:**
1. **NextAuth.js** -- готовое решение, провайдеры (Google, GitHub), session management
2. **JWT вручную (jsonwebtoken + jose)** -- ручная реализация, полный контроль
3. **Server sessions (cookie + DB)** -- классический подход

**Выбор:** JWT вручную

**Обоснование:**
- Простота: `auth.ts` -- 120 строк. `createSessionToken`, `getSession`, `setSessionCookie`, `requireAuth`, `requireAdmin`, `requireSuperAdmin`. Все.
- Edge Runtime: Next.js middleware (`middleware.ts`) работает в V8 Isolates, а не в Node.js. `jsonwebtoken` использует Node.js `crypto` и не совместим с Edge. Решение: `jose` (Edge-совместимая) для middleware, `jsonwebtoken` для API routes.
- Нет внешних провайдеров: нам не нужен Google/GitHub OAuth. Только email + пароль.
- NextAuth конфигурация: `[...nextauth].ts` + PrismaAdapter + CredentialsProvider + session callbacks -- избыточная сложность для нашего случая.

**Компромиссы:**
- Нет CSRF-защиты (компенсируется: SameSite=Lax, httpOnly cookie).
- Нет автоматического refresh token (компенсируется: токен на 7 дней, для хакатона достаточно).
- Нет blacklist токенов при logout (токен остается валидным, но cookie удаляется).

## DR-005: 3 роли (SUPER_ADMIN, ADMIN, USER) vs 2 роли

**Дата:** День 1

**Контекст:** ТЗ явно не определяет систему ролей. Нужно решить: плоская структура (admin/user) или иерархическая.

**Рассмотренные варианты:**
1. **2 роли (ADMIN, USER)** -- проще, но один админ на всю систему
2. **3 роли (SUPER_ADMIN, ADMIN, USER)** -- мультитенантность, делегирование

**Выбор:** 3 роли

**Обоснование:**
- Мультитенантность: SUPER_ADMIN управляет всей системой (все компании), ADMIN привязан к конкретной компании (`companyId`). Это позволяет нескольким компаниям использовать одну инсталляцию.
- Делегирование: SUPER_ADMIN создает ADMIN-ов для компаний-заказчиков. ADMIN-ы самостоятельно управляют своими сотрудниками, группами, импортом XML.
- Роль USER: сотрудники видят только свои курсы и прогресс (личный кабинет, readOnly Ганта). Без этой роли сотрудники либо не имеют доступа, либо видят чужие данные.

**Компромиссы:**
- Усложнение каждого API endpoint (проверка роли + фильтрация where-clause).
- Матрица доступа из ~20 строк (см. architecture.md, раздел 3).

## DR-006: Employee != User -- разделение сущностей

**Дата:** День 1

**Контекст:** Employee (участник обучения из ERP) и User (аккаунт в системе) -- это одно и то же или разные сущности?

**Рассмотренные варианты:**
1. **Единая модель User** -- все сотрудники = пользователи, одна таблица
2. **Две модели с optional 1:1 связью** -- Employee существует без User, User может быть связан с Employee

**Выбор:** Раздельные модели с optional связью

**Обоснование:**
- XML-импорт: из Global ERP приходят участники обучения (Employee). У них нет учетных записей -- они не пользуются системой. Создавать пустые User-записи для тысяч сотрудников бессмысленно.
- Инвайт-ссылки: только когда сотруднику нужен доступ, админ создает инвайт. При регистрации User привязывается к существующему Employee через `employeeId`.
- Автопривязка: если User не связан с Employee явно, система пытается найти Employee по совпадению email. Fallback для случаев, когда инвайт создан раньше импорта сотрудника.

**Компромиссы:**
- Дополнительная логика при каждом запросе USER: сначала найти `user.employeeId`, потом `employee.companyId`, потом фильтровать данные.
- Возможна рассинхронизация: Employee и User с одинаковым email, но без связи. Митигация: автопривязка по email.

## DR-007: JSON customFields vs жесткая схема -- гибридный подход

**Дата:** День 1

**Контекст:** Компании имеют стандартные реквизиты (ИНН, КПП, ОГРН), но могут иметь произвольные дополнительные поля ("расчетный счет", "банк", "ОКВЭД").

**Рассмотренные варианты:**
1. **Только фиксированные колонки** -- добавлять поля через миграции
2. **Только JSON** -- все реквизиты в одном JSON-поле
3. **Гибрид: фиксированные + customFields (JSON)** -- стандартные поля индексируются, остальное -- JSON

**Выбор:** Гибридный подход

**Обоснование:**
- Стандартные поля (`inn`, `kpp`, `ogrn`, `address`, `phone`, `email`, `contactPerson`) -- отдельные колонки. Индексируются, типизируются, участвуют в поиске.
- `customFields: Json? @default("{}")` -- произвольные данные. Не нужны миграции для каждого нового клиента.
- PostgreSQL `jsonb` -- нативная поддержка, индексы по JSON-путям (если понадобится).

**Компромиссы:**
- customFields не типизируются на уровне Prisma -- любой JSON принимается.
- Нет валидации структуры customFields -- ответственность на фронтенде.

## DR-008: Автогенерация кодов компаний -- транслитерация

**Дата:** День 2

**Контекст:** У каждой компании должен быть уникальный код (2-4 символа по ТЗ). Ручной ввод неудобен и ведет к дублям.

**Рассмотренные варианты:**
1. **Обязательный ручной ввод** -- пользователь вводит код, система проверяет уникальность
2. **UUID-based** -- первые 4 символа CUID -- нечитаемые
3. **Транслитерация + auto-increment** -- "ТехноПром" -> TEH-001

**Выбор:** Транслитерация + auto-increment

**Обоснование:**
- Алгоритм: убрать организационно-правовую форму (ООО, АО, ПАО...) и кавычки, взять первые 3 буквы, транслитерировать в латиницу, добавить порядковый номер (`-001`, `-002`...).
- Читаемый результат: "TEH-001" -- понятно человеку и машине.
- Код можно переопределить вручную (если поле `code` передано в POST -- используется оно, иначе автогенерация).

**Компромиссы:**
- Коллизии префиксов: "ТехноПром" и "ТехноПарк" -> оба TEH-*. Разрешается инкрементом: TEH-001, TEH-002.
- Транслитерация не идеальна: "Щ" -> "SCH" (3 символа из 1). Для 3-буквенного префикса это некритично.

## DR-009: Soft delete с корзиной -- возможность отката

**Дата:** День 2

**Контекст:** Админ может случайно удалить курс или группу. Нужен механизм восстановления.

**Рассмотренные варианты:**
1. **Полное удаление (hard delete)** -- DELETE FROM ... CASCADE. Необратимо.
2. **Флаг isDeleted** -- дополнительная колонка в каждой таблице, фильтрация в каждом запросе.
3. **Отдельная таблица DeletedItem** -- JSON-снимок данных перед удалением.

**Выбор:** Таблица DeletedItem (корзина)

**Обоснование:**
- Не нужно модифицировать каждую модель (добавлять `isDeleted`, `deletedAt`).
- Не нужно менять каждый `findMany` (добавлять `where: { isDeleted: false }`).
- JSON-снимок (`entityData`) сохраняет все данные, включая связи. Можно восстановить полностью.
- SUPER_ADMIN видит корзину и может восстановить объект.

**Компромиссы:**
- При восстановлении связи (FK) могут быть нарушены, если связанные объекты тоже удалены. Нужна ручная проверка.
- JSON-снимок может быть большим (группа с 50 участниками). Для хакатона -- приемлемо.

## DR-010: window.location.href vs Next.js Link -- стабильность навигации

**Дата:** День 2

**Контекст:** При клике по полосе на диаграмме Ганта нужно перейти к карточке группы. Next.js Link использует клиентскую навигацию (SPA), window.location.href -- полную перезагрузку.

**Рассмотренные варианты:**
1. **Next.js `<Link>` / `router.push()`** -- SPA-навигация, мгновенный переход, сохранение state
2. **`window.location.href`** -- полная перезагрузка страницы

**Выбор:** `window.location.href`

**Обоснование:**
- Стабильность: SPA-навигация в сложных случаях (SVG-клик внутри Ганта, переход из модального окна) может вызывать проблемы с state. `window.location.href` гарантирует чистую загрузку страницы.
- bfcache: кнопка "Назад" в браузере может показать устаревший state (stale data). Middleware устанавливает `Cache-Control: no-store` для HTML-страниц, что запрещает bfcache.
- Для хакатона скорость перехода (200ms vs мгновенно) некритична.

**Компромиссы:**
- Каждый переход -- полная загрузка страницы (~200ms). Для SaaS с тысячами переходов неприемлемо, для хакатона -- приемлемо.
- Потеря клиентского state при навигации (фильтры, позиция скролла). Компенсируется серверным рендерингом.

## DR-011: Resend vs Nodemailer -- отправка email

**Дата:** День 2

**Контекст:** Нужна отправка email для инвайт-ссылок и уведомлений о начале/завершении обучения.

**Рассмотренные варианты:**
1. **Nodemailer + SMTP-сервер** -- классический подход, нужен SMTP (Yandex, Gmail, свой)
2. **SendGrid** -- SaaS, 100 писем/день бесплатно, сложная настройка (domain verification)
3. **Resend** -- SaaS, 100 писем/день бесплатно, один npm-пакет + API-ключ

**Выбор:** Resend

**Обоснование:**
- Минимальная настройка: `npm install resend`, один API-ключ в `.env`, `onboarding@resend.dev` работает для тестирования без верификации домена.
- API: `resend.emails.send({ from, to, subject, html })` -- 1 вызов.
- 100 писем/день бесплатно -- для демо хакатона достаточно.
- Не нужен SMTP-сервер (Nodemailer требует конфигурацию SMTP host/port/auth).

**Компромиссы:**
- Vendor lock-in на Resend. Для production-среды стоит рассмотреть Nodemailer + собственный SMTP.
- Тестовый домен `onboarding@resend.dev` не подходит для production (письма могут попадать в спам).

## DR-012: Модули курса -- расширяемость для аналитики

**Дата:** День 2

**Контекст:** ТЗ требует только "курс обучения" как сущность. Стоит ли детализировать структуру курса?

**Рассмотренные варианты:**
1. **Курс -- плоская сущность** -- название, длительность, цена. Без внутренней структуры.
2. **Курс с модулями** -- Course -> CourseModule (лекция, практика, тест, задание) с порядком и длительностью.

**Выбор:** Курс с модулями

**Обоснование:**
- Детализация учебного плана: HR-менеджер видит, из чего состоит курс (5 лекций, 3 практики, 1 тест).
- Подготовка для будущей аналитики: прогресс по модулям, а не только по группе. Хотя в текущей версии прогресс хранится на уровне GroupMember, модули создают фундамент для детализации.
- Типы модулей (enum: `LECTURE`, `PRACTICE`, `TEST`, `ASSIGNMENT`) -- стандартные для корпоративного обучения.
- `orderIndex` -- порядок модулей в курсе. `durationHours` -- длительность каждого модуля.

**Компромиссы:**
- Дополнительная сложность: CRUD для модулей, UI для управления порядком.
- Прогресс пока хранится на уровне группы (0-100%), а не на уровне модуля. Расширение возможно в будущем.

## DR-013: Prisma ORM vs Drizzle -- выбор ORM

**Дата:** День 1

**Контекст:** Нужен ORM для PostgreSQL с поддержкой TypeScript и миграций.

**Рассмотренные варианты:**
1. **Prisma** -- декларативная схема, генерация типов, миграции
2. **Drizzle** -- SQL-like API, легче, ближе к raw SQL
3. **TypeORM** -- декораторы, Active Record/Data Mapper
4. **Raw SQL** -- максимальный контроль, нулевая абстракция

**Выбор:** Prisma

**Обоснование:**
- Единый файл `schema.prisma` (280 строк) описывает все 13 моделей, связи, enum-ы, индексы. Читается как документация.
- Генерация типов: `prisma.trainingGroup.findMany({ include: { course: true, members: true } })` -- TypeScript знает, что результат содержит `course` и `members[]`.
- Миграции: `prisma migrate dev` создает SQL-файлы в `prisma/migrations/`. `prisma migrate deploy` применяет их в production (Dockerfile: `npx prisma migrate deploy`).
- `prisma studio` -- GUI для просмотра и редактирования данных (полезно при отладке).

**Компромиссы:**
- Prisma Client -- тяжелее Drizzle (~2MB vs ~100KB в бандле).
- Некоторые сложные запросы (window functions, recursive CTE) невозможны через Prisma -- нужен `$queryRaw`.
- Генерация клиента добавляет шаг в build: `npx prisma generate`.

## DR-014: Lazy update статусов vs Cron job

**Дата:** День 2

**Контекст:** Статусы групп (PLANNED -> IN_PROGRESS -> COMPLETED) должны обновляться автоматически по датам.

**Рассмотренные варианты:**
1. **Cron job** -- фоновая задача обновляет статусы каждый час/день
2. **Lazy update** -- статусы обновляются при каждом запросе `GET /api/groups`
3. **Триггер PostgreSQL** -- обновление на уровне БД

**Выбор:** Lazy update

**Обоснование:**
- Нет необходимости в дополнительной инфраструктуре (cron, очередь задач).
- Статусы всегда актуальны при отображении пользователю.
- `GET /api/groups` выполняет проверку дат для каждой группы. Если дата начала прошла и статус PLANNED -- обновляем на IN_PROGRESS. Если дата окончания прошла и статус IN_PROGRESS -- обновляем на COMPLETED.
- Обновления батчатся: `Promise.all(statusUpdates)`.

**Компромиссы:**
- Если никто не заходит в систему 3 дня -- статусы не обновятся до первого запроса. Для корпоративной системы (ежедневное использование) это не проблема.
- Небольшой overhead на каждый GET (проверка дат + UPDATE). Для ~100 групп -- незначительно.

## DR-015: Фиксация цены группы vs ссылка на текущую цену курса

**Дата:** День 2

**Контекст:** Группа создается с определенной ценой за человека. Что если цена курса изменится позже?

**Рассмотренные варианты:**
1. **Ссылка на цену курса** -- `totalCost = course.pricePerPerson * memberCount`. При изменении цены курса все группы пересчитываются.
2. **Фиксация цены** -- `trainingGroup.pricePerPerson` копируется из курса при создании. Далее независимо.

**Выбор:** Фиксация цены

**Обоснование:**
- Бизнес-логика: если компания договорилась на 50,000 руб/чел, а через месяц курс подорожал до 60,000 -- ранее созданные группы сохраняют старую цену.
- Спецификация (юридический документ) ссылается на стоимость группы. Ретроактивное изменение цены нарушило бы юридическую целостность.
- `PriceHistory` отдельно фиксирует историю цен курса для анализа динамики.

**Компромиссы:**
- Если цена курса обновляется -- существующие группы не обновляются автоматически. Нужно вручную менять `pricePerPerson` в группе.
- Два источника правды: `course.pricePerPerson` (текущая цена) и `trainingGroup.pricePerPerson` (зафиксированная). Может вызвать путаницу у пользователя.

## DR-016: CSV с BOM и ";" vs стандартный CSV с ","

**Дата:** День 2

**Контекст:** Экспорт отчетов в CSV для открытия в Excel. Данные содержат кириллицу.

**Рассмотренные варианты:**
1. **Стандартный CSV** -- запятая-разделитель, UTF-8 без BOM
2. **CSV с BOM и ";"** -- BOM маркер (\uFEFF) + точка с запятой

**Выбор:** CSV с BOM и ";"

**Обоснование:**
- Microsoft Excel на Windows по умолчанию открывает CSV в кодировке Windows-1251 и с разделителем ";". Без BOM-маркера кириллица отображается как "кракозябры".
- BOM (\uFEFF) -- 3 байта в начале файла, которые подсказывают Excel использовать UTF-8.
- Точка с запятой -- стандартный разделитель для русской локали Excel (запятая используется как десятичный разделитель в русском формате чисел).

**Компромиссы:**
- Нестандартный CSV -- сторонние программы (Python pandas, Google Sheets) могут некорректно обработать BOM или ожидать запятую. Для целевой аудитории (HR-менеджеры с Excel) -- приемлемо.
